# ADR-009 — Environment, migration and recovery release boundary
Status: Proposed, 2026-09-13. TASK-026 planning only.

## Context
Local verification is strong but does not establish cloud release safety, restore integrity or operator responsibility. Database migrations and MFA keys must be recovered with clinical versions/audits; destructive schema rollback is prohibited.

## Proposed decision
Separate local, synthetic staging and production resources/data/identities. Build immutable artifacts once. Use a single least-privilege migration job before ECS rollout, additive/backward-compatible migrations, deployment circuit-breaker rollback for application failures and roll-forward for incompatible schema. Use RDS PITR/snapshots and a separately protected KMS-backed MFA key. Restore into a new database and validate tenant counts, memberships, document snapshots, amendments, audit timestamps and MFA before traffic switching.

Propose staging RPO/RTO 24h/8h and production-pilot RPO/RTO 5m/4h for owner/operations acceptance after drills. Backup retention and legal record retention remain different, unresolved policies. Never copy production data to staging or automatically delete records/backups.

## Consequences / open decision
Compatible releases require extra migration design and pre-release checks. Multi-AZ handles availability, while PITR/restore drills handle recovery; neither substitutes for incident ownership. Final objectives, retention, cross-region/account backup, operator roles and go-live authority remain Open.

## Verification required before acceptance
TASK-030 must run synthetic migration, rollback/roll-forward, PITR/restore, key recovery, integrity and incident-tabletop scenarios. Sources: `Documentation/Project/DEPLOYMENT_PLAN.md`.
