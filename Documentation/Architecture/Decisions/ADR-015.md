# ADR-015 — Separate synthetic staging runtime and operator jobs

Status: Accepted for owner-approved local TASK-028 preparation, 2026-09-20. No cloud activation, spend, production acceptance or deletion authorization. Extends ADR-014; preserves ADR-008/009 and their unresolved deployed decisions.

Keep the packaged HTTP/loopback runtime unchanged. Add a distinct staging composition root requiring synthetic scope, exact HTTPS origin, verified PostgreSQL TLS with explicit CA and separate runtime credentials, origin authentication, cookie-only sessions and KMS-wrapped identity key versions. CloudFront/ALB supply and validate an origin header; application validates it before API routes. Internal health checks are the only bypass and expose no clinical data. CloudFront uses zero TTL for all behaviors/errors; preserve credential/origin/practice headers and cookies. Exact shell routing never turns API errors into cached HTML.

Retain private foundation resources and add a complementary application stack. Only ALB has internet routing, restricted to the CloudFront managed prefix list and TLS. Fargate/RDS stay private. A two-stage optional foundation OAC grant avoids competing ownership of the S3 bucket policy. Task count zero and custody false are configuration defaults, not spending controls: even applying inactive infrastructure would incur charges and remains unauthorized.

Use separate non-serving bootstrap and migration tasks. Bootstrap can obtain owner credentials, creates missing roles and rejects unexpected existing privileges without changing their passwords or revoking grants. Migration owns schema and explicitly grants reviewed table permissions; runtime has no persistent-schema DDL, record deletion/truncation or history update grant. Preserve immutable database triggers and existing migrations. New/unexpected table owners require review. These privileges are verified in local PostgreSQL; actual RDS operator restrictions still need deployed proof.

Synthetic delivery uses a retained encrypted EFS access point, TLS/IAM and UID1000 with private files. A separately invoked read-only retrieval task has no database/identity secret, network mail or EFS write grant. It seals one UUID-selected message using AES-256-GCM and RSA-OAEP-SHA256 to an operator public key; cloud logs contain ciphertext only. Private-key decryption writes an exclusive ignored 0600 local file and never prints the token. Operator identity, run/pass-role permissions and CloudTrail evidence require later scoped approval. No general clinical user gains operator access. Delivery conflicts/failed writes retain evidence for explicit reconciliation; no purge.

Serving and mailbox images remain distroless/non-root. Migration remains separately classified, with unresolved scanner findings in FIND-013; isolated job identity is not vulnerability remediation or risk acceptance. TLS, runtime config, database-role denials/audit rollback, sealed-message recovery and infrastructure policy checks provide local evidence only. Real IAM/KMS/EFS/TLS/provider behavior, cost model/anomaly delivery, operator alerts/recovery and target-clinic connectivity remain unverified. No Philippine legal/clinical/privacy/signature/retention finding is resolved.

## Additive migration candidate — 2026-09-21

Accepted for the same approved local preparation scope: add `migration-hardened` alongside the original `migration` stage. Copy the frozen installed Prisma CLI closure and platform-native engine, bundle the existing database operator command, and retain the required OpenSSL runtime libraries/package metadata. Use the existing UID1000 with an additional passwd entry; all base accounts remain. No shell, global npm/pnpm, frontend or test dependency closure is needed in this separate candidate. The original full image/package graph remains available, with its findings unchanged. Do not imply that the new image supports seed/generate/dev commands: its verified contract is bootstrap/migrate and native migrate status.

Native Prisma migration TLS uses `sslmode=require`, `sslaccept=strict` and an explicit `sslcert` CA path; a bare require flag is insufficient. The node-postgres runtime/role connections retain explicit CA plus rejectUnauthorized=true. Real-image tests demonstrate native wrong-CA and wrong-hostname rejection as well as successful repeated migrations, original checksums and separate runtime grants. No trust-all fallback. Direct CLI mode pins the copied engine and disables update checks; the original pnpm invocation remains supported. Scans and inventories are artifact-specific, not a legal/security certification or authorization to run remote jobs. See TASK-028 acceptance for exact local evidence.
