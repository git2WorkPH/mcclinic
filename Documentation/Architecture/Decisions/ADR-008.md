# ADR-008 — AWS Singapore synthetic-staging topology
Status: Proposed, 2026-09-13. TASK-026 planning only.

## Context
The current API is intentionally loopback-only, web uses a Vite proxy, PostgreSQL runs in local Compose and onboarding delivery/key storage use `.local`. The target audience is in the Philippines, with connectivity quality varying by location/provider. A deployment path must preserve the modular monolith and tenant/clinical boundaries.

## Proposed decision
Evaluate `ap-southeast-1` through real clinic measurements. For managed synthetic staging, use private S3 + CloudFront for built web assets and same-origin routing; CloudFront sends uncached `/mvp/graphql` requests to ALB → one ARM ECS Fargate modular-monolith task → private single-AZ RDS PostgreSQL `mcclinic`. Use separate environment resources, Secrets Manager/KMS, ECR, CloudWatch and least-privilege runtime/migration roles. Production pilot raises API tasks to two across AZs and RDS to Multi-AZ after TASK-030 evidence.

Do not cache authenticated API/document responses, expose RDS, use Kubernetes/microservices, or introduce offline synchronization. Retain the local loopback entry point. A $12 Lightsail VM is a documented lower-cost staging alternative, not the production recommendation.

## Consequences / open decision
Managed ECS/ALB improves repeatable releases and rollback but adds roughly $30–40/month over the Lightsail alternative before database/CDN. CloudFront improves asset delivery and connection setup but does not remove origin/internet dependence. Private-task egress (NAT versus endpoints/controlled alternative), final region, domain/account ownership and measured cost/latency remain for approval in TASK-028. No resource exists by this ADR.

## Verification required before acceptance
Current AWS Calculator estimate, real target-ISP comparison, infrastructure threat/cost review, uncached authorization tests and deployed tenant/network smoke evidence. Sources: `Documentation/Project/DEPLOYMENT_PLAN.md`.
