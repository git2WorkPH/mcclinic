# ADR-011 — Practice-enabled modules and diagnostic adapters

Status: Proposed, 2026-09-14. No implementation or architecture acceptance implied.
Context: owner wants subscribed practices to optionally add laboratory, X-ray, 2D echo and later capabilities. Current modular monolith, memberships, subscriptions and laboratory design seam support extension, but no module installation platform exists.

## Proposed decision

- Ship reviewed feature modules with platform releases; expose a practice feature catalog and activation/configuration records. “Install” is practice activation, not downloaded arbitrary code, per-tenant deploy or database fork.
- Keep practice activation, commercial entitlement, platform module availability, connector readiness and actor/resource authorization separate. Enforce their applicable combination server-side, including jobs/media; feature hiding is presentation only.
- Keep domain ownership and ports/adapters. Diagnostic modules reference authorized patient/encounter/history interfaces. Shared code is limited to demonstrated delivery/storage/identity primitives; modality-specific clinical logic stays owned by its module.
- Build transport-neutral lab/imaging contracts before selecting vendor adapters. Potential standards do not establish a provider's compatibility. External lab/PACS services may remain external; do not turn the app into internal microservices for this requirement.
- Stage imaging as report/reference handling, then selected archive/viewer support. DICOM/PACS and diagnostic viewer validation are independent projects from attaching an image or PDF. 2D echo media/measurements need their own assessment.
- Suspend new clinical creation/transmission on deactivation while preserving authorized records/export and handling in-flight results explicitly. Do not purge records on uninstall/downgrade. Safe historical access must survive compatible release rollback.
- Prefer metadata-first/on-demand media and resumable transfers over full-study automatic downloads. Do not introduce offline synchronization.

## Alternatives and consequences

A client-only feature flag is insufficient for paid access or patient privacy. An arbitrary plugin marketplace adds untrusted execution, dependency, migration, support and security obligations without a present need. Per-practice code deployments complicate upgrades and identity isolation. Proposed managed modules keep deployment simple but require a real registry, consistent policy checks, shared-schema additive migrations, per-practice setup and lifecycle tests. Storage and integration delivery details need further ADRs before implementation.

Open: pricing/entitlement model, activation permissions, first diagnostic workflow/vendor, DICOM/viewer requirements, long-running transfer/storage limits, in-flight disable semantics and production clinical/privacy rules (FIND-014–016).

Traceability: REQ-PROD-002, REQ-FOUND-013/014, REQ-FEAT-016–018; TASK-036–040. Preserves ADR-001/005/006 and existing local development restrictions.
