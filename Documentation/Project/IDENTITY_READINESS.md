# Identity preparation and remaining production gates

Local synthetic scope only. TASK-029 remains in progress. Preserve the original local mailbox mode.

## Durable delivery testing

The API supports `IDENTITY_DELIVERY_MODE=outbox` with an explicit `IDENTITY_SYNTHETIC_DOMAINS=example.test`. Unset mode preserves the old synchronous local mailbox. The outbox worker polls once per second, claims 60-second leases and retries up to eight attempts with exponential backoff capped at one hour. Exhausted records are retained; operators inspect metadata counts, never tokens in logs. No real mail adapter is active. The test sink uses outbox UUID filenames to deduplicate retry after acknowledgement failure. A failed/corrupt sink file is retained and reports an idempotency conflict rather than overwriting it.

Run `pnpm db:generate` then `pnpm exec vitest run tests/outbox.integration.test.ts tests/onboarding.integration.test.ts tests/identity-keyring.test.ts` with Docker running. Database tests use isolated synthetic Testcontainers, not the clinic database. Before opting an existing local container into this mode, apply the additive migration with its migration image. Existing images remain available for rollback. No production environment flag is enabled.

## Key custody and recovery

`IDENTITY_KEYRING_FILE` optionally points at an absolute private JSON file (mode 0600): fields `active` (key ID) and `keys` (map of key IDs to base64 32-byte random keys). Generate keys using a cryptographic random source outside tracked files. Back up all versions plus the original `onboarding-key`; verify a separate restore before changing the active ID. New encrypted records carry an authenticated version prefix. Keep old keys and ciphertext; do not purge or rewrite records automatically. A missing version fails closed.

This local file adapter is not KMS-backed. Production still needs least-privilege KMS wrapping, a separately recoverable encrypted key inventory, rotation/operator audit, no secret-bearing outputs and deployed enrolled-account recovery evidence. No key deletion is authorized.

## Implementation update — 2026-09-20

The baseline above is retained as decision history. Local preparation now includes the following implementations; actual AWS/provider deployment remains unverified.

- `IDENTITY_COOKIE_ORIGIN` opts the packaged API into exact HTTPS-origin cookie authentication. It requires an HTTPS reverse proxy; setting it on the existing HTTP-only clinic is not a supported browser setup. Cookies use `__Host-`, HttpOnly, Secure, SameSite=Strict and an eight-hour maximum matching database sessions. Only same-origin JSON POST requests are allowed. Login returns `cookie-session`, a nonsecret UI marker, including through GraphQL aliases. Authorization bearer headers are ignored in cookie mode. Logout revokes the stored session and clears the cookie. The built React Native Web client and proxy support this mode; local self-signed HTTPS browser tests cover login/reload/logout and secret isolation. Default local bearer behavior remains unchanged.
- Persistent per-username login budgets apply in cookie mode as well as the existing in-process throttle and database MFA/onboarding counters. Default: ten attempts per fifteen-minute bucket, including successful logins; production edge/IP controls still need deployment validation.
- `IDENTITY_KMS_ENVELOPE_FILE` selects an absolute path to a wrapped key envelope. It cannot be combined with `IDENTITY_KEYRING_FILE`. Constructing the SDK provider requires the separate `IDENTITY_KMS_ALLOW_NETWORK=true` activation switch. **Leave that switch unset for this approved local-only work.** No AWS call has been made. The prepared adapter pins Singapore, binds the exact KMS ARN, application/environment/version encryption context, validates returned key identity/length and loads keys into memory. Local injected-provider tests exercise unwrap, failure and backup round trips; actual KMS permissions, wrapping and CloudTrail evidence are not proven.
- Wrapped envelope shape: `active`, `environment` equal to `synthetic-staging`, `kmsKeyArn`, and `keys` mapping version IDs to base64 KMS ciphertext blobs. Never put plaintext keys or real envelopes into tracked examples. Authorized future operators must wrap each 32-byte data key with the identical context expected by the adapter, preserve all previous versions and test a separately restored envelope before rotation. No automatic re-encryption or deletion occurs. Legacy ciphertext still requires its original `onboarding-key` backup.
- A real PostgreSQL test enrolls MFA under the first key, switches the active key while retaining the first, restores the key file separately and verifies enrolled-account login. It does not stand in for the eventual AWS disaster-recovery drill.
